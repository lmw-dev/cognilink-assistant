# 02-CogniLink 项目概要与规划

Owner: 明伟 刘
Created time: April 23, 2025 8:41 PM

## 1. 引言与愿景

### 1.1. 问题陈述

知识工作者、开发者和内容创作者在跨不同工具和数据源进行信息整合、原创内容生成以及复杂工作流管理时，常常面临效率低下的挑战。现有的工具可能缺乏与个人知识库（如 Obsidian）的深度集成，或者无法在特定工作流中根据上下文有效利用先进的 AI 能力。AI 工具的整合往往需要大量的手动操作或复杂的自定义设置，严重阻碍了生产力。核心问题在于缺乏**上下文感知**的任务执行，用户需要能够理解其特定知识领域和工作流上下文的 AI 助手，并能与相关工具和数据无缝交互。

### 1.2. 愿景与目标

开发一款智能助手工具，该工具能深度集成用户的知识库（初期聚焦于 Obsidian），并通过标准化协议（如 MCP）利用 AI 模型（如 Claude、GPT）来简化工作流程、增强内容创作能力、促进研究与分析。

- **目标1:** 在用户主要的工作环境（初期为 Obsidian）中提供无缝的、上下文感知的 AI 辅助。
- **目标2:** 通过统一界面，实现与本地知识（Obsidian 笔记、文件）和潜在的外部工具/数据源的交互。
- **目标3:** 增强内容创作工作流，提供尊重原创性和署名权的 AI 支持。
- **目标4:** 提供灵活且可扩展的架构，倾向于利用 MCP 进行工具集成。

## 2. 产品概述：形态、用户与用例

### 2.1. 建议产品形态

项目目前聚焦于开发 **Obsidian 插件**形态的 CogniLink Assistant。

- **优点：** 与用户的知识库深度集成，利用现有的 Obsidian UI/API，直接访问笔记/元数据，对 Obsidian 用户来说是熟悉的环境。
- **核心考量：** 需要仔细考虑安全性，并可能需要构建/捆绑或依赖 MCP 服务器来实现与知识库或外部工具的交互。

### 2.2. 目标用户画像

- **知识工作者/研究人员：** 使用 Obsidian 进行笔记记录、研究整合和写作，需要 AI 帮助连接想法、总结资料。
- **内容创作者/博主：** 利用 Obsidian 进行构思、起草、管理内容，需要 AI 辅助大纲生成、草稿撰写、图片查找等。
- **开发者/技术主管：** 同时使用 IDE 和知识库进行工作，需要将 AI 集成到编码环境中，理解代码库并与开发工具交互。

### 2.3. 关键用例

- **上下文感知 AI 聊天：** 与 AI 对话，AI 理解当前 Obsidian 笔记或选定文本的上下文。
- **知识整合与摘要：** 总结 Obsidian 笔记内容，确保原创性和署名。
- **内容生成与增强：** 辅助生成大纲、起草文本段落、建议内部链接。
- **研究辅助：** 对 Obsidian 库进行语义查询，检索信息。

## 3. 高层需求（功能与非功能）

### 3.1. 功能需求 (FR) 概要

- **核心 AI 交互：** 提供聊天界面，连接 LLM API (Claude, GPT 等)，支持 API 密钥配置和上下文感知。
- **Obsidian 集成：** 读取笔记内容、访问元数据、执行库内搜索、笔记操作、管理标签。
- **MCP 客户端实现 (潜在)：** 连接并管理 MCP 服务器，发现工具，促进 LLM 与工具交互，实现用户同意机制。
- **内容创作辅助：** 基于上下文生成大纲、起草段落、建议链接，潜在集成图像工具。
- **原始材料引用 (RAG)：** 基于 Obsidian 库内容提供来源识别、检索、增强生成和归因。
- **原创性检测 (库内相似度)：** 评估文本与用户 Obsidian 库内容的相似度，帮助识别自我重复。

### 3.2. 非功能需求 (NFR) 概要

- **性能：** 确保 UI 响应迅速，AI 响应及时。
- **可扩展性：** 设计应能处理大型 Obsidian 库。
- **安全性：** 安全处理 API 密钥，遵守 MCP 安全实践，解决本地文件访问风险，减轻 MCP 服务器和提示注入风险。
- **可用性与用户体验 (UX)：** 提供直观界面，遵循 Obsidian/扩展 UX 最佳实践，提供清晰反馈。
- **可靠性与稳定性：** 确保与 API/服务器连接稳定，优雅处理错误。
- **可维护性：** 采用模块化架构设计。
- **伦理 AI：** 减轻偏见，确保透明度，遵守负责任 AI 原则。

## 4. 高层架构与关键集成

### 4.1. 高层架构

插件将遵循标准的 Obsidian 插件架构，核心模块包括：

- **核心模块：** 处理用户界面、命令处理和工作流编排。
- **AI 交互模块：** 管理与 LLM API 的通信、提示处理、上下文管理。
- **Obsidian 交互层：** 使用 Obsidian API 与库交互（读/写笔记、元数据、搜索）。
- **配置模块：** 管理用户设置（API 密钥、模型选择等）。
- **RAG/原创性模块：** 处理嵌入向量存储、语义搜索、相似度计算和归因逻辑（初期采用直接 API 集成 LLM，未来可能引入 MCP）。

### 4.2. 关键集成点

- **LLM APIs：** Anthropic (Claude), OpenAI, Google 等。
- **Obsidian API：** 直接与 Obsidian 库数据和功能交互。
- **MCP 服务器 (未来考虑)：** Filesystem, Web Search, Git, Linear 等，用于扩展功能和与其他工具集成。

## 5. 开发规划概要

项目将采用分阶段的迭代开发模型，与 Linear Cycles 对齐，并使用 Milestones 标记主要成就。

### 5.1. 开发阶段概要

- **阶段 1: MVP (Minimum Viable Product):** 实现核心 AI 交互（聊天），基础 Obsidian 集成（读取当前笔记上下文），以及连接一个 LLM API。
- **阶段 2: Beta 发布：** 增强 Obsidian 集成（搜索、元数据），支持更多 LLM，实现核心内容创作功能（大纲、草稿），引入基础的 RAG/原创性辅助。
- **阶段 3: V1.0 发布：** 完善所有核心功能，全面的测试和文档，优化的用户体验，可能包含更高级的集成。

### 5.2. 关键里程碑概要

- **M1 (阶段 1 结束)：** MVP 演示，具备基础 AI 聊天和 Obsidian 读取访问。
- **M2 (阶段 2 中期)：** Beta 版本，支持更多 LLM 和库搜索。
- **M3 (阶段 2 结束)：** Beta 候选版本，具备核心内容生成和 RAG/原创性基础功能。
- **M4 (阶段 3 中期)：** 功能完整版本，包含高级辅助功能。
- **M5 (阶段 3 结束)：** V1.0 发布，包含完整测试、文档和优化。

### 5.3. 技术栈考量

- **主要技术：** TypeScript (Obsidian 插件开发语言)，Obsidian API。
- **AI 交互：** 直接调用 LLM 提供商的 API。
- **项目管理：** Linear (用于 Issue 跟踪、周期和里程碑管理)。
- **开发环境：** Cursor IDE (结合 AI 辅助编码)，Git (版本控制)。

### 5.4. 资源与团队

- **团队：** 当前团队规模为 1-2 人。
- **所需技能：** 熟悉 TypeScript/JavaScript，了解 AI/LLM API，熟悉 Obsidian 插件开发。
- **其他资源：** 需要考虑 AI API 使用费用，以及应对 MCP 生态系统发展潜在变化的资源投入。
