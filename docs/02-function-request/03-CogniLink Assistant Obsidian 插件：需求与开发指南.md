# 03-CogniLink Assistant Obsidian 插件：需求与开发指南

Owner: 明伟 刘
Created time: April 23, 2025 8:42 PM

## 1. 引言与范围

### 1.1. 目的

本指南旨在为 CogniLink Assistant Obsidian 插件项目提供一份详细的需求说明、技术设计考量和可操作的开发工作流程指引。CogniLink Assistant 是一个旨在增强 Obsidian 笔记记录和知识管理体验的 AI 助手，通过集成 AI 能力提供上下文感知辅助、笔记合成和潜在的任务自动化功能。

### 1.2. 范围

本文档详细阐述 CogniLink Assistant Obsidian 插件以下方面的具体内容：

- 核心功能（聊天界面、原始材料引用/RAG、原创性检测）的详尽需求。
- 技术设计、架构和集成策略。
- 插件开发相关的安全与伦理考量。
- 使用 Linear 进行项目管理和结合 Cursor 进行开发的具体工作流程。
- Obsidian 插件开发的详细任务分解和阶段计划。

本文档假设读者具备 Obsidian、IDE（特别是 VS Code 或 Cursor）以及基础项目管理概念的相关知识。

## 2. 详细功能需求 (FR)

### 2.1. 聊天界面

聊天界面是用户与插件交互的核心。

- **FR 2.1.1 UI 容器与布局：** 应嵌入标准的 Obsidian 侧边栏视图或面板，遵循 Obsidian UI 模式。
- **FR 2.1.2 输入区域：** 提供文本输入框，支持 Markdown，包含发送按钮并支持 Enter 提交 (可配置 Shift+Enter)。
- **FR 2.1.3 消息显示：** 按时间顺序显示用户/AI 消息，AI 回复支持 Markdown 渲染，AI 处理时有视觉指示，支持复制消息/代码块。
- **FR 2.1.4 对话管理：** 允许新会话，对话历史持久化存储在 Obsidian 库中 (.chat 文件或特定文件夹)，支持重命名、搜索和删除历史会话。
- **FR 2.1.5 上下文处理与提示工程：** 允许包含当前笔记/选定文本作为上下文，管理对话上下文（Token 限制、手动包含/排除、钉住关键信息、自动截断），支持可配置系统提示/前导指令模板。
- **FR 2.1.6 UI/UX 最佳实践：** 遵循通用 UX 原则（清晰、一致、反馈、防错、简洁），界面响应迅速不阻塞主 UI，提供清晰视觉提示，考虑可访问性。

### 2.2. 原始材料引用 (RAG 集成)

利用 RAG 使 AI 回答基于 Obsidian 库内容并提供引用。

- **FR 2.2.1 来源识别与检索：** 从库中识别/检索相关信息，实现语义搜索（嵌入向量），利用 Obsidian 结构信息（链接、标签、元数据）提高相关性，嵌入向量本地存储管理。
- **FR 2.2.2 增强与生成：** 将检索到的文本片段和用户提示传递给 LLM，通过提示工程指导 LLM 基于上下文生成答案（减少幻觉），上下文不足时明确指出。
- **FR 2.2.3 归因机制：** 清晰追溯 AI 回复到来源笔记，支持多种显示方法（内联、列表、UI 集成），引用链接到源笔记，在检索中传递必要元数据实现准确归因，解决多来源综合归因挑战。
- **FR 2.2.4 避免（自我）剽窃：** 鼓励信息整合转述而非直接复制，清晰区分 AI 生成和直接引用文本。

### 2.3. 原创性检测

评估文本相对于 Obsidian 库内容的相似度。

- **FR 2.3.1 定义：** 主要聚焦评估目标文本与用户 Obsidian 库中现有内容的相似度（非绝对原创性或 AI 生成判定）。
- **FR 2.3.2 检测方法：** 实现语义相似度（嵌入向量比较） 或 N-gram 重叠，方法需在插件环境中计算可行。
- **FR 2.3.3 用户界面与报告：** 提供触发检查方式，以易于理解方式呈现相似度结果（百分比、高亮、链接至相似笔记），允许配置检测设置。
- **FR 2.3.4 伦理考量：** 清晰说明方法局限性/不准确性，确保过程尊重用户隐私，优先本地分析。

## 3. 详细非功能需求 (NFR)

- **NFR 3.1 性能：** 确保 UI 交互响应迅速，AI 响应及时，最小化 MCP 工具调用延迟（未来）。
- **NFR 3.2 可扩展性：** 处理大型 Obsidian 库，有效管理 MCP 服务器连接（未来）。
- **NFR 3.3 安全性：** 安全处理 API 密钥，遵守 MCP 安全最佳实践（未来），解决本地文件访问风险，减轻 MCP 服务器（未来）和提示注入风险。
- **NFR 3.4 可用性与用户体验 (UX)：** 提供直观界面，遵循 Obsidian 插件 UX 最佳实践，提供清晰反馈。
- **NFR 3.5 可靠性与稳定性：** 确保与 API/服务器连接稳定，优雅处理错误。
- **NFR 3.6 可维护性：** 采用模块化架构设计。
- **NFR 3.7 伦理 AI：** 减轻偏见，确保透明度，遵守负责任 AI 原则。

## 4. 技术设计与架构

### 4.1. 高层架构

遵循标准的 Obsidian 插件架构，模块包括：

- **UI 组件：** 使用 Obsidian 支持的技术（如 React/Svelte/HTML）。
- **核心逻辑：** TypeScript/JavaScript。
- **AI 交互模块：** 处理与 LLM API 的通信。
- **Obsidian 交互层：** 使用 Obsidian API 与库交互。
- **配置模块：** 管理设置。
- **RAG/原创性模块：** 嵌入向量存储、语义搜索、相似度计算等。

### 4.2. AI 模型集成

- 支持主流 LLM API 集成 (OpenAI, Anthropic 等)。
- 用户安全配置 API 密钥。
- 考虑支持本地 LLM (Ollama, LM Studio API)。
- 抽象 LLM 交互层。

### 4.3. 数据流

- **聊天：** 用户输入 -> 上下文组装 -> LLM API 调用 -> 回复渲染。
- **引用 (RAG)：** 用户查询 -> 语义搜索 -> 上下文检索 -> LLM API 调用 (增强提示) -> 回复生成 -> 归因格式化 -> 回复渲染。
- **原创性检查：** 目标文本 -> 嵌入向量计算 -> 库内比较 -> 相似度评分 -> 结果显示。

### 4.4. 集成方法：直接 API vs. MCP

- **初期：** 优先采用**直接 API 集成**与 LLM 交互，降低初期复杂性。
- **未来：** 架构具备模块化，未来可重构以支持 MCP，增强互操作性。
- **原因：** 直接 API 调用对核心功能足够，MCP 增加设置复杂度和开发开销，生态系统仍在发展。

## 5. 集成策略

### 5.1. Obsidian 核心功能交互

- 利用 Obsidian API 读取笔记、元数据、链接。
- 使用 Obsidian Markdown 渲染引擎。
- 与 Obsidian 搜索集成 (语义搜索可能自定义)。
- 使用 Obsidian 通知系统提供反馈。
- 在命令面板注册关键命令。

### 5.2. 插件依赖

- 尽量减少对其他社区插件的依赖。
- 如果依赖，清晰说明并优雅处理缺失情况。

### 5.3. 配置

- 在 Obsidian 设置区域提供专用标签页。
- 允许用户配置 AI 提供商/模型、API 密钥（安全存储）、默认系统提示、上下文管理设置、原创性检测设置、功能开关。
- 遵循设置界面 UX 最佳实践。

## 6. 安全与伦理考量

### 6.1. API 密钥管理

- 密钥绝不能明文存储，应利用安全存储机制。
- 对外部 API 调用使用 HTTPS。

### 6.2. 数据隐私

- 清晰告知用户哪些数据发送到外部 API。
- 遵守 LLM 提供商隐私政策。
- 本地文件访问需严格限制范围并请求明确用户许可。
- 设计优先考虑用户控制、透明度和本地处理。

### 6.3. AI 输出透明度与可靠性

- 清晰标记 AI 生成内容。
- 为 RAG 回复提供来源引用。
- RAG 失败或未使用时显示警告。
- 提供 AI 模型信息。

### 6.4. 偏见缓解

- 承认 LLM 潜在偏见。
- 允许用户选择不同模型。
- 鼓励用户批判性评估 AI 输出。

## 7. 开发计划与工作流程

### 7.1. 开发阶段与任务 (Obsidian 插件)

以下是针对 Obsidian 插件的更详细开发任务分解，与项目概要中的阶段相对应：

- **阶段 1: 基础与核心 AI (MVP)**
  - 设置 Obsidian 插件项目基础结构和构建配置。
  - 集成一个 AI 提供商 API 并实现安全密钥处理。
  - 实现基本上下文检索（当前笔记）。
  - 开发初始 Prompt 策略。
  - 构建最小化聊天 UI (侧边栏)。
  - 设置基本单元测试框架。
- **阶段 2: 功能扩展 (Beta)**
  - 实现高级上下文 - 链接笔记。
  - 实现高级上下文 - 标签与元数据。
  - 实现对话历史管理。
  - 构建插件设置 UI。
  - 集成 Obsidian 命令。
  - 探索 RAG 实现（如果决定实施，将创建新的 Feature/Task）。
- **阶段 3: 测试与优化 (Beta Release)**
  - 全面测试（单元测试、集成测试）。
  - 内部 Alpha/Beta 测试计划。
  - Bug 修复与性能调优。
  - UI/UX 优化。
  - Prompt 优化。
- **阶段 4: 发布与文档 (V1.0)**
  - 编写用户文档。
  - 准备社区插件发布。
  - 提交到 Obsidian 社区插件列表。
  - 建立反馈与支持渠道。
  - 规划维护策略。

### 7.2. 工作流程指南：结合 Linear 与 Cursor

本插件开发将采用结合 Linear 和 Cursor 的高效工作流。

- **Linear 配置：**
  - 创建 Linear 项目（"CogniLink Assistant Obsidian Plugin"）。
  - 配置工作流状态（Backlog, Todo, In Progress, Code Review, Testing, Done 等）。
  - 利用 Cycles（周期）进行迭代管理。
  - 使用 Milestones（里程碑）跟踪主要阶段。
  - 定义 Labels（标签）进行 Issue 分类（类型、领域、优先级）。
  - 创建 Issue Templates（模板）标准化 Bug 报告和功能请求。
- **Issue 创建规则：**
  - Feature Issue 作为父级，代表主要功能。
  - Task Issue 作为子级，代表实现 Feature 所需的具体步骤。
  - 使用标题格式 "Feature: [摘要]" 和 "Task: [摘要]"。
  - 为 Issue 分配类型、标签和负责人。
- **Cursor 与 Linear 集成 (通过 MCP - 未来可能)：**
  - **MCP 作为集成桥梁：** MCP 使 AI 代理与外部服务（如 Linear）通信。
  - **Cursor 内配置 (未来 MCP 集成时)：** 在 .cursor/mcp.json 文件中配置 Linear MCP 服务器，安全存储 API 密钥。
  - **Cursor 内交互示例 (未来 MCP 集成时)：** 在 Cursor 中使用 @Linear 等方式调用工具创建、搜索或更新 Issue。
  - **局限性与安全考量 (未来 MCP 集成时)：** 注意 Cursor MCP 限制、MCP 生态成熟度、API 密钥安全、本地服务器执行风险和 Prompt 注入风险。
- **自动化进度跟踪 (未来)：** 利用 Linear 的 Git 集成自动关联提交和 PR，通过自动化平台集成 CI/CD 事件。
- **协作与反馈：** Linear 作为单一事实来源，清晰的交接点，收集反馈并纳入迭代。
