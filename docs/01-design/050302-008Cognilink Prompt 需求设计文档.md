## **Cognilink Prompt 模块详细需求设计文档**

版本: 1.0  
日期: 2025年5月31日

### **1\. 引言**

#### **1.1. 文档目的**

本文档旨在详细定义 Cognilink 插件中 Prompt 模块的功能需求、设计规范、数据结构及技术实现要点。它将作为产品、设计和开发团队进行 Prompt 模块设计、开发、测试和迭代的依据。

#### **1.2. 项目背景与模块概述**

Cognilink 插件致力于提升用户在 Obsidian 中的内容创作和知识管理效率。Prompt 模块是 Cognilink 的核心组件之一，它允许用户通过预设或自定义的模板，结合动态上下文，生成结构化、高质量的 Prompt，从而驱动 AI 更精准地完成内容生成任务。此模块需要支持跨多种内容平台（如小红书、Twitter/X、微信公众号、个人博客、头条号等）的 Prompt 最佳实践，帮助用户针对不同平台的特性优化内容。

#### **1.3. 模块目标**

* **提升内容质量与平台适应性**：通过结构化和平台优化的 Prompt，帮助用户生成更符合特定平台风格和算法偏好的高质量内容。  
* **提高用户效率**：提供模板管理和自动渲染功能，简化用户构建复杂 Prompt 的过程。  
* **增强可定制性与灵活性**：允许用户创建、修改和管理自己的 Prompt 模板，以适应个性化的工作流程和多变的内容需求。  
* **促进品牌一致性**：通过模板化的 Prompt，帮助用户在不同平台输出风格一致的品牌内容。

### **2\. 范围**

#### **2.1. 包含范围**

* Prompt 模板的创建、读取、更新、删除（CRUD）功能。  
* 默认 Prompt 模板的提供与恢复。  
* Prompt 模板的导入与导出功能。  
* 基于平台特性的模板分类或标签管理。  
* 支持动态变量（如 ${theme}, ${context}, ${pinned}, ${platform\_specific\_instructions} 等）的模板结构。  
* 在内容生成流程中自动渲染和应用选定的 Prompt 模板。  
* 集成于 Obsidian 插件设置界面的模板管理用户界面。

#### **2.2. 不包含范围 (未来可能考虑)**

* AI 辅助生成 Prompt 模板本身。  
* Prompt 模板的社区分享与市场。  
* Prompt 的 A/B 测试与性能分析功能。  
* 过于复杂的条件逻辑或脚本语言在模板中的嵌入。

### **3\. 目标用户**

* 使用 Cognilink 插件在 Obsidian 中进行内容创作的个人用户（如博主、知识工作者、研究人员）。  
* 需要为不同社交媒体或内容平台生成定制化内容的用户。  
* 希望提高 AI 内容生成效率和质量的用户。

### **4\. 功能需求**

#### **4.1. Prompt 模板管理**

基于 1 中的核心需求，并扩展对多平台的支持：

* **4.1.1. 模板 CRUD 操作**  
  * **创建 (Create)**：用户应能通过 UI 创建新的 Prompt 模板，定义模板名称、内容和可选的平台分类/标签 1。  
  * **读取 (Read)**：用户应能在设置界面查看所有可用模板列表，包括模板名称、内容预览和平台分类/标签 1。  
  * **更新 (Update)**：用户应能编辑现有模板的名称、内容和平台分类/标签 1。  
  * **删除 (Delete)**：用户应能删除自定义模板，删除前应有确认提示 1。  
* **4.1.2. 默认模板管理**  
  * 系统应提供一组预定义的默认 Prompt 模板，这些模板应包含通用结构以及针对主流平台（小红书、Twitter/X、微信公众号、个人博客、头条号）优化过的示例 1。  
  * 用户应能将任意一个可用模板（包括自定义模板和预定义模板）设置为“默认 Prompt 模板”，用于内容生成时的自动调用 1。  
  * 用户应能一键恢复系统最初提供的所有默认模板，此操作不应删除用户自定义模板，但会将默认模板设置恢复为系统初始值 1。  
* **4.1.3. 模板导入/导出**  
  * 用户应能将选定的一个或多个 Prompt 模板导出为 JSON 或 Markdown 文件，便于备份和分享。  
  * 用户应能从本地导入符合特定格式（JSON/Markdown）的 Prompt 模板文件。  
* **4.1.4. 平台分类/标签 (新增)**  
  * 系统应允许用户为每个模板关联一个或多个平台标签（例如：“小红书”、“Twitter”、“博客通用”、“微信深度文”）。  
  * 模板列表中应能显示这些标签，并可能支持按标签筛选。  
  * 预定义的默认模板应自带相关的平台标签。

#### **4.2. Prompt 模板结构与变量**

基于 1 中的核心需求：

* **4.2.1. 模板内容**  
  * 模板内容为纯文本，支持多行输入。  
  * 模板内容通过占位符支持动态变量的嵌入 1。  
* **4.2.2. 变量系统**  
  * 支持预定义的核心变量，如：  
    * ${theme}: 用户输入的主题或核心指令 1。  
    * ${context}: 从 Obsidian 笔记中提取的上下文信息 1。  
    * ${pinned}: 用户固定的关键信息或参考资料 1。  
    * ${date}: 当前日期（可自定义格式）。  
    * ${user\_name}: 当前 Obsidian 用户名（如果可获取）。  
  * **新增平台适应性变量/结构化提示 (建议)**：  
    * ${platform\_name}: 模板对应的目标平台名称（例如，由模板分类自动带入或用户指定）。  
    * ${output\_format\_suggestion}: 根据平台特性建议的输出格式（例如，“小红书笔记格式，包含标题、正文、标签、封面建议”）。  
    * ${tone\_style\_guidance}: 针对特定平台的语气和风格建议（例如，“Twitter：简洁、有力、可加入emoji；微信公众号：专业、深入、逻辑清晰”）。  
    * ${engagement\_hook\_prompt}: 提示用户思考或AI辅助生成用于吸引平台用户的钩子。  
    * ${cta\_prompt}: 提示用户思考或AI辅助生成适用于特定平台的行动号召。  
    * ${hashtag\_suggestion\_prompt}: 提示用户思考或AI辅助生成相关标签。  
  * 变量语法统一为 ${variableName} 1。

#### **4.3. Prompt 渲染与生成**

基于 1 中的核心需求：

* **4.3.1. 自动渲染**：在 Cognilink 的内容生成工作流（例如，通过主题输入模态框提交时），系统应自动获取当前选定的默认 Prompt 模板 1。  
* **4.3.2. 变量替换**：系统应使用实际的上下文值（如用户输入的主题、提取的笔记内容等）替换模板中的变量占位符，生成最终的 Prompt 字符串 1。  
* **4.3.3. 传递给 AI 服务**：渲染后的完整 Prompt 字符串将被传递给后续的 AI 服务进行内容生成 1。

#### **4.4. 平台特定指导与最佳实践 (新增)**

* **4.4.1. 模板创建/编辑时的提示**：当用户创建或编辑模板时，如果选择了平台分类/标签，UI 界面可以动态展示与该平台相关的 Prompt 编写最佳实践、注意事项或关键要素（例如，小红书的CES评分机制、Twitter的字符限制和信息流结构、博客的SEO要点等）。这些提示信息可以预置在系统中。  
* **4.4.2. 预定义模板的教育意义**：提供的针对各平台的默认模板本身应作为最佳实践的范例，用户可以通过研究这些模板学习如何为不同平台构建高效 Prompt。

#### **4.5. 用户界面 (UI) \- Prompt 模板管理**

基于 1 中 SettingsTab.tsx 的设计，并进行细化：

* **4.5.1. 主界面**  
  * 在 Cognilink 插件的设置页面中，设立一个明确的“Prompt 模板管理”区域 1。  
  * **模板列表** 1：  
    * 以列表形式展示所有可用的 Prompt 模板。  
    * 每项模板应显示：模板名称、内容预览（例如，前 N 个字符或首行）、平台分类/标签、是否为默认模板的标识（例如，星号图标）。  
    * 提供排序功能（按名称、按修改日期、按平台标签）。  
    * 提供筛选功能（按平台标签、按是否为自定义/默认）。  
  * **操作按钮区**：  
    * “新增模板”按钮：点击后弹出模板创建/编辑模态框 1。  
    * “导入模板”按钮。  
    * “导出选中模板”按钮（列表支持多选）。  
    * “恢复默认模板”按钮：点击后有确认提示，执行恢复操作 1。  
* **4.5.2. 模板列表项操作** 1  
  * **编辑按钮**：打开模态框，预填当前模板信息供用户修改。  
  * **删除按钮**：仅对自定义模板可见，点击后有确认提示。  
  * **设为默认按钮**：将该模板设为内容生成时默认使用的模板。当前默认模板应有高亮或其他视觉提示。  
  * **复制/克隆按钮**：允许用户快速复制一个现有模板作为新模板的基础。  
* **4.5.3. 模板创建/编辑模态框**  
  * **模板名称输入框**：必填。  
  * **模板内容输入区**：多行文本编辑器，支持 ${variableName} 语法高亮（可选）。  
  * **平台分类/标签选择器**：允许用户选择或输入多个平台标签。  
  * **可用变量提示区**：展示当前系统支持的所有可用变量及其含义，方便用户在模板内容中引用。  
  * **平台最佳实践提示区 (动态)**：根据选择的平台标签，显示相关的编写指导。  
  * “保存”和“取消”按钮。

### **5\. 非功能需求**

* **5.1. 性能**  
  * 模板列表加载和渲染应在1秒内完成。  
  * Prompt 渲染（变量替换）过程对用户几乎无感知，不应显著增加内容生成前的等待时间。  
* **5.2. 易用性**  
  * 模板管理界面应直观易懂，用户无需查阅文档即可完成基本操作。  
  * 变量的使用和模板的创建应尽可能简单。  
  * 错误提示清晰友好。  
* **5.3. 可靠性**  
  * 用户创建和修改的模板数据应能被持久化可靠存储在 Obsidian 的插件设置中或指定文件中 1。  
  * 导入/导出功能应能正确处理数据格式。  
* **5.4. 可扩展性**  
  * 未来应能方便地增加新的预定义默认模板。  
  * 未来应能方便地扩展支持新的变量类型或更复杂的模板逻辑（若有需求）。  
* **5.5. 兼容性**  
  * 模块应与 Cognilink 插件的现有架构和 Obsidian 的版本兼容。

### **7\. 技术设计与架构 (参考** 1**)**

* **7.1. PromptTemplateService.ts** 1  
  * **职责**：负责模板的加载、存储、增删改查、渲染等核心逻辑。  
  * **方法 (示例)**：  
    * loadTemplates(): PromptTemplate: 从存储中加载所有模板。  
    * saveTemplates(templates: PromptTemplate): void: 将模板保存到存储。  
    * getTemplateById(id: string): PromptTemplate | undefined: 根据ID获取模板。  
    * getDefaultTemplate(): PromptTemplate | undefined: 获取当前默认模板，若无则返回系统第一个默认模板 1。  
    * renderTemplate(template: PromptTemplate, variables: Record\<string, string\>): string: 替换模板中的变量，生成最终 Prompt 1。  
    * addTemplate(templateData: Omit\<PromptTemplate, 'id' | 'createdAt' | 'updatedAt'\>): PromptTemplate: 新增模板。  
    * updateTemplate(id: string, updates: Partial\<PromptTemplate\>): PromptTemplate | undefined: 更新模板。  
    * deleteTemplate(id: string): boolean: 删除模板。  
    * restoreDefaultTemplates(): PromptTemplate: 恢复系统默认模板。  
* **7.2. 模板存储** 1  
  * 优先考虑存储在 Obsidian 插件的 data.json 设置文件中（通过 this.plugin.settings.cognilinkPromptSettings）。  
  * 备选方案：独立的 JSON 文件存储在插件配置目录下，例如 .obsidian/plugins/cognilink/prompt-templates.json。  
* **7.3. 变量替换机制** 1  
  * 使用正则表达式或简单的字符串替换方法处理 ${variableName} 格式的占位符。  
  * 需注意处理变量名中可能存在的特殊字符，以避免替换错误或安全问题。  
* **7.4. 错误处理**  
  * 在文件读写、模板查找、渲染等环节加入充分的错误处理和日志记录。

### **8\. 与 Cognilink 及 Obsidian 的集成 (参考** 1**)**

* **8.1. Obsidian 设置集成** 1  
  * 模板管理的用户界面将作为 Cognilink 插件设置页 (SettingsTab.tsx) 的一个独立部分呈现。  
  * 所有模板数据和默认模板ID的设置将通过 Obsidian 提供的插件 API 进行持久化存储。  
* **8.2. 主工作流集成** 1  
  * 在用户触发内容生成操作时（例如，在 ThemeInputModal 中提交主题后），Cognilink 的主逻辑会：  
    1. 实例化 PromptTemplateService。  
    2. 调用 getDefaultTemplate() 获取当前应使用的模板。  
    3. 收集必要的变量值（如 theme, context, pinned 等）。  
    4. 调用 renderTemplate() 方法生成最终的 Prompt 字符串。  
    5. 将渲染后的 Prompt 传递给 AIService 或相应的 AI 调用模块。

### **9\. 未来考虑与潜在增强**

* **高级变量类型**：支持更复杂的变量，如从预定义列表中选择（例如，语气选择：专业/幽默/中性），或布尔型变量控制模板某部分的包含与否。  
* **模板内条件逻辑**：允许在模板中使用简单的条件语句（例如，如果某个上下文变量为空，则使用不同的提示语）。  
* **Prompt 片段/组件化**：允许用户定义可复用的 Prompt 片段，并在多个模板中引用。  
* **AI 辅助模板优化**：集成 AI 能力，根据用户输入的主题或目标平台，向用户推荐合适的模板或优化现有模板。  
* **更深度的 Obsidian 上下文集成**：自动提取更多类型的 Obsidian 上下文作为可用变量（例如，当前笔记的标签、链接、任务列表等）。  
* **多语言支持**：模板内容和UI支持多语言。
