# **Obsidian社交媒体内容生成插件：需求设计文档 (MVP)**

## **1\. 引言**

### **1.1 本文档目的**

本文档旨在详细定义 Obsidian 社交媒体内容生成插件（以下简称“本插件”或“Cognilink”）的最小可行产品 (MVP) 的功能需求、非功能需求、系统架构、模块设计、数据模型及部署策略。它将作为独立开发者进行产品开发、测试和迭代的基础。

### **1.2 产品愿景**

赋能 Obsidian 用户，特别是独立内容创作者，将其在 Obsidian 中积累的知识笔记高效、自动地转化为适用于主流社交媒体平台（如微信公众号、今日头条、小红书、Twitter/X、个人博客等）的、具有一定原创性和高质量的、符合平台特性的内容，从而放大个人知识的价值与影响力。

### **1.3 范围 (MVP 核心)**

本 MVP 版本将聚焦于实现从用户 Obsidian 笔记到针对特定社交媒体平台的初稿文章生成的核心流程。功能将包括：

* 基于用户笔记的高效 RAG (Retrieval Augmented Generation) 上下文检索。  
* 针对 1-2 个核心社交媒体平台的平台化提示工程。  
* 调用 LLM (Large Language Model) 生成内容。  
* 基础的内部原创性检测（与源笔记比较）。  
* 简洁易用的 Obsidian 插件用户界面。  
* 稳定的本地 Python AI 后端服务。

高级功能如复杂的知识图谱构建、全面的外部原创性检测、高级自动化评估流水线、LLM 微调等将作为后续迭代方向。

### **1.4 目标用户**

* 使用 Obsidian 进行知识管理和笔记撰写的个人用户。  
* 需要在多个社交媒体平台发布内容的自媒体创作者、博主、知识分享者。  
* 希望提高内容生产效率，同时保持一定原创性和个人风格的用户。

## **2\. 系统概述**

### **2.1 核心架构选择**

本插件采用**混合架构** 1：

* **前端 (Obsidian 插件)**: 使用 JavaScript/TypeScript 开发，负责用户界面 (UI)、用户交互 (UX)、与 Obsidian Vault 的数据交互，并通过本地 HTTP 请求与 Python 后端通信。  
* **后端 (本地 Python AI 服务器)**: 使用 FastAPI 框架开发，承载所有计算密集型 AI/NLP 任务，如文本处理、向量嵌入、RAG 检索、LLM 调用、内容分析等。该服务器由插件在后台管理其生命周期。

此架构旨在平衡 Obsidian 的深度集成与 Python 在 AI 领域的强大能力，同时为独立开发者提供可管理的复杂性。

### **2.2 核心模块 (MVP)**

1. **Python AI 服务器 (后端)**  
   * 向量数据库与 RAG 管道模块  
   * 平台化提示工程模块  
   * LLM 内容生成接口模块  
   * 实用原创性检测模块  
   * API 服务模块 (FastAPI)  
2. **Obsidian 插件 (前端)**  
   * 用户界面与交互模块  
   * 与 Python 后端通信模块  
   * Python 后端管理模块 (简化版)  
3. **核心工作流服务** (串联前后端逻辑)

## **3\. 功能需求 (MVP)**

### **3.1 用户认证与配置**

* **FR-CONF-001**: 用户应能在插件设置中配置连接本地 Python AI 服务器的地址和端口（提供默认值，并允许用户修改以解决潜在冲突）。  
* **FR-CONF-002**: 用户应能在插件设置中安全地配置所选 LLM 服务的 API Key。API Key 应在本地加密存储或引导用户使用环境变量。  
* **FR-CONF-003 (可选 MVP)**: 用户应能配置 RAG 检索的 Top-K 值和语义相似度阈值。  
* **FR-CONF-004 (可选 MVP)**: 用户应能配置内部原创性检测的相似度阈值。

### **3.2 Obsidian 笔记处理与 RAG 管道**

#### **3.2.1 笔记选择/输入**

* **FR-RAG-001**: 用户应能通过插件界面选择一篇或多篇当前 Obsidian Vault 中的笔记作为内容生成的主要灵感来源。  
* **FR-RAG-002**: 用户应能直接在插件界面输入一个主题或关键词作为内容生成的起点。

#### **3.2.2 文本分块 (后端实现)**

* **FR-RAG-003**: 系统应能对用户选定的 Markdown 笔记内容进行智能分块。  
* **FR-RAG-004**: 分块策略应优先采用 Markdown 感知的方法，如首先按H1/H2/H3等标题进行结构化分割，然后对大块内容进行递归字符分割（基于 Markdown 常用分隔符） 1。  
* **FR-RAG-005**: 分块大小应基于 Token 数量，并能适应嵌入模型和 LLM 的上下文窗口限制（例如，目标块大小 256-512 tokens）1。  
* **FR-RAG-006**: 分块时应支持设置合理的块重叠（如块大小的10-20%）以保持语义连贯 1。  
* **FR-RAG-007**: 每个文本块应附加源笔记路径、标题等元数据 1。

#### **3.2.3 向量嵌入与存储 (后端实现)**

* **FR-RAG-008**: 系统应使用指定的句向量模型（如 all-MiniLM-L6-v2 或优质中文模型）为文本块生成嵌入向量 1。  
* **FR-RAG-009**: 系统应使用 **LanceDB** 作为本地向量数据库，存储文本块内容、嵌入向量及相关元数据 1。  
* **FR-RAG-010**: 向量数据库应支持笔记新增、修改、删除时对应向量数据的增量更新或重建（MVP阶段可简化为手动触发重建或基于文件修改时间戳的简单更新）。

#### **3.2.4 语义检索与上下文组装 (后端实现)**

* **FR-RAG-011**: 系统应能根据用户输入的主题/关键词（或选定笔记的核心内容）的向量表示，在 LanceDB 中进行 Top-K 语义相似度搜索，检索最相关的笔记块 1。  
* **FR-RAG-012**: 系统应对检索到的笔记块进行去重（基于路径或高相似度嵌入），避免过多重复信息输入LLM 1。  
* **FR-RAG-013**: 系统应能组装最终输入 LLM 的上下文，优先考虑用户可能指定的“核心笔记/段落”（若支持此功能），然后按相似度排序加入检索到的笔记块。  
* **FR-RAG-014**: 系统必须严格控制输入 LLM 的上下文总 Token 数量，超出部分进行智能截断 1。

### **3.3 平台特定内容生成**

#### **3.3.1 社交媒体平台选择**

* **FR-GEN-001**: 用户应能在插件界面选择一个目标社交媒体平台（MVP阶段支持单选，如博客、小红书、微信公众号中的1-2个）1。

#### **3.3.2 提示模板管理 (MVP: 内置)**

* **FR-GEN-002**: 系统应内置针对 MVP 支持的社交媒体平台的高质量基础提示模板 1。  
* **FR-GEN-003 (后端实现)**: 提示模板应支持动态变量替换，如 {theme}, {retrieved\_context}, {platform\_style\_guide}, {desired\_length} 等 1。  
* **FR-GEN-004 (后端实现)**: 系统应能根据用户选择的目标平台和输入，加载并填充相应的提示模板，生成最终的 LLM 输入提示 1。

#### **3.3.3 LLM 调用 (后端实现)**

* **FR-GEN-005**: 系统应能稳定调用用户在设置中配置的（或默认的）云端 LLM API（如 OpenAI GPT 系列）1。  
* **FR-GEN-006**: LLM 调用接口应能处理认证、请求参数（如模型、温度、最大Token数）和基本的错误重试逻辑 1。

### **3.4 内部原创性检测**

#### **3.4.1 相似度计算 (后端实现)**

* **FR-ORI-001**: 系统应能将 LLM 生成的社交媒体帖子内容按句子或短段落分割 1。  
* **FR-ORI-002**: 系统应能计算每个生成片段的嵌入向量，并将其与RAG检索过程中使用的源笔记块的嵌入向量进行余弦相似度比较 1。  
* **FR-ORI-003**: 系统应使用可配置的相似度阈值（默认为0.85）来识别与源笔记内容高度相似的片段 1。

#### **3.4.2 UI 高亮显示相似内容 (前端实现)**

* **FR-ORI-004**: 插件界面在展示生成内容时，应对被检测为与源笔记高度相似的片段进行明显的视觉高亮 1。  
* **FR-ORI-005**: 高亮片段应能提示用户其与哪个源笔记（或片段）相似，鼓励用户修改以增强表达新鲜度。

### **3.5 用户界面与交互 (Obsidian 插件)**

#### **3.5.1 主生成视图/模态框**

* **FR-UI-001**: 插件应提供一个简洁直观的入口（如Ribbon图标、命令面板命令）来打开主生成视图（可以是模态框或侧边栏面板）。  
* **FR-UI-002**: 输入界面应包含：  
  * 笔记选择器（从当前Vault选择）或主题/关键词输入框。  
  * 目标社交媒体平台选择器（MVP为单选下拉菜单或按钮组）。  
  * (可选MVP) 风格倾向选择（如正式/活泼）、期望大致长度范围的简单选项。  
  * “生成内容”按钮。  
* **FR-UI-003**: 点击“生成内容”后，界面应显示清晰的加载状态或进度指示，因为后端处理可能耗时。

#### **3.5.2 结果展示与编辑**

* **FR-UI-004**: 生成结果应在同一视图或新视图中清晰展示，若选择了多平台（未来迭代），则应能方便切换查看各平台内容。  
* **FR-UI-005**: 生成内容中的原创性高亮应如 FR-ORI-004 所述。  
* **FR-UI-006**: 应提供基础的文本编辑功能，允许用户在插件内对生成的草稿进行修改。  
* **FR-UI-007**: 应提供“一键复制”生成内容到剪贴板的功能。  
* **FR-UI-008**: 应提供将生成内容“插入到当前笔记”或“创建为新笔记”的功能。  
* **FR-UI-009 (可选MVP)**: 展示用于生成该内容的RAG源笔记列表，方便用户追溯和参考。

#### **3.5.3 设置面板**

* **FR-UI-010**: 插件应提供一个标准的Obsidian设置面板页面。  
* **FR-UI-011**: 设置面板应包含 FR-CONF-001 至 FR-CONF-004 中定义的所有可配置项。  
* **FR-UI-012**: API Key 等敏感信息输入字段应使用密码类型。

### **3.6 Python 后端管理 (简化版 MVP)**

* **FR-MGMT-001**: 插件加载时，应尝试检查本地 Python 后端服务是否已运行（例如，通过尝试连接预设的本地端口）。  
* **FR-MGMT-002**: 若后端服务未运行，插件应尝试在后台启动已打包的 Python 可执行程序（如果实现了打包和自动启动）。若无法自动启动，应向用户提供清晰的指引，告知如何手动启动后端服务。  
* **FR-MGMT-003**: 插件卸载或 Obsidian 关闭时，应尝试向 Python 后端服务发送关闭信号。  
* **FR-MGMT-004**: 插件应能处理后端服务启动失败、连接不上的基本异常情况，并向用户提供友好的错误提示和故障排除建议。

## **4\. 非功能需求 (MVP)**

* **NFR-PERF-001 (性能)**: 对于中等大小的笔记输入和标准社交媒体帖子长度，从点击生成到内容展示的端到端时间应尽可能控制在用户可接受范围内（例如，目标在15-60秒内，具体取决于LLM响应速度）。RAG检索过程不应成为明显瓶颈。  
* **NFR-USAB-001 (易用性)**: 插件界面应简洁直观，符合 Obsidian 用户的使用习惯，学习成本低。  
* **NFR-RELI-001 (可靠性)**: MVP 版本应能稳定运行核心功能流程，避免频繁崩溃或产生严重错误。  
* **NFR-SECU-001 (安全性)**:  
  * 用户 LLM API Key 等敏感配置应在本地安全存储（例如，使用 Obsidian 提供的存储API，避免明文存储在易被访问的文件中）。  
  * 所有与笔记内容相关的处理（分块、嵌入、RAG）均在本地 Python 服务器完成，用户笔记数据不应未经用户明确同意发送到任何外部第三方服务（LLM调用除外，且用户已知晓）。  
* **NFR-MAIN-001 (可维护性)**: 代码（前端和后端）应采用模块化设计，注释清晰，便于独立开发者后续的迭代和维护。  
* **NFR-INST-001 (可安装性)**:  
  * Obsidian 插件部分应遵循标准的社区插件安装方式。  
  * Python 后端部分的安装和启动应尽可能简化。MVP 阶段可提供详细的手动安装和启动指南，或一个简单的启动脚本。将后端打包成可执行文件是推荐方向。

## **5\. 详细模块设计 (MVP)**

### **5.1 Python AI 服务器 (FastAPI)**

#### **5.1.1 向量存储模块 (LanceDB 封装)**

* **目的**: 负责与 LanceDB 交互，实现笔记块向量的存储、更新和检索。  
* **输入**: 文本块数据 (内容、元数据)、查询向量。  
* **核心逻辑**:  
  * add\_documents(docs: List): 将分块后的文档（含嵌入向量）批量写入 LanceDB。处理已存在文档的更新逻辑。  
  * delete\_document(note\_path: str): 删除指定笔记相关的所有向量数据。  
  * search(query\_vector: List\[float\], top\_k: int, similarity\_threshold: float) \-\> List: 执行语义搜索并返回结果。  
* **输出**: 检索到的文本块列表 (含内容、元数据、相似度分数)。  
* **关键依赖**: lancedb, sentence-transformers。

#### **5.1.2 文本处理模块 (分块)**

* **目的**: 将 Markdown 笔记内容分割成适合处理的文本块。  
* **输入**: Markdown 文本内容。  
* **核心逻辑**:  
  * chunk\_markdown\_text(text: str, config: ChunkConfig) \-\> List: 实现 FR-RAG-004 至 FR-RAG-007 定义的分块策略。  
* **输出**: 包含文本内容和元数据的文本块对象列表。  
* **关键依赖**: langchain.text\_splitter (MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter), tiktoken。

#### **5.1.3 RAG 服务模块**

* **目的**: 编排 RAG 流程，从用户输入到组装好的 LLM 上下文。  
* **输入**: 用户查询 (文本)、源笔记路径列表 (可选)、RAG配置参数。  
* **核心逻辑**:  
  * get\_rag\_context(query: str, source\_note\_paths: List\[str\] \= None, config: RAGConfig) \-\> str:  
    1. 若提供源笔记路径，则优先处理这些笔记；否则，根据查询文本的嵌入在整个向量库中搜索。  
    2. 对选定笔记进行分块和嵌入（如果尚未索引或需要更新）。  
    3. 执行向量检索 (调用向量存储模块)。  
    4. 对检索结果进行去重和排序。  
    5. 根据 Token 限制组装最终的上下文字符串。  
* **输出**: 格式化后的上下文字符串，准备送入提示模板。

#### **5.1.4 提示工程服务模块**

* **目的**: 管理和渲染平台特定的提示模板。  
* **输入**: 目标平台ID、动态变量字典 (包含主题、RAG上下文等)。  
* **核心逻辑**:  
  * load\_prompt\_templates(file\_path: str) \-\> Dict: 从文件加载提示模板。  
  * render\_prompt(platform\_id: str, variables: Dict\[str, Any\]) \-\> str: 根据平台ID和变量渲染最终提示。  
* **输出**: 准备好发送给 LLM 的完整提示字符串。

#### **5.1.5 LLM 交互服务模块**

* **目的**: 封装与 LLM API 的交互。  
* **输入**: 完整提示字符串、LLM配置参数 (模型名称、温度、API Key等)。  
* **核心逻辑**:  
  * generate\_text(prompt: str, llm\_config: LLMConfig) \-\> str: 调用指定的 LLM API，处理请求和响应，包含错误处理和重试。  
* **输出**: LLM 生成的文本内容。

#### **5.1.6 原创性检测服务模块**

* **目的**: 检测生成内容与源笔记的相似部分。  
* **输入**: 生成的文本内容、用于RAG的源笔记块列表 (含嵌入)。  
* **核心逻辑**:  
  * check\_internal\_originality(generated\_text: str, source\_chunks: List, threshold: float) \-\> List: 实现 FR-ORI-001 至 FR-ORI-003 定义的检测逻辑。  
* **输出**: 高相似度片段的位置信息和来源信息列表。

#### **5.1.7 API 端点 (FastAPI)**

* **/initialize\_vector\_store (POST)**: 触发对用户整个 Vault 或指定文件夹的笔记进行索引/更新。  
  * 请求: (可选) folder\_path: str  
  * 响应: status: str, message: str  
* **/generate\_social\_post (POST)**: 核心内容生成接口。  
  * 请求: query: str (主题/关键词), source\_note\_paths: List\[str\] (可选), target\_platform: str, llm\_config: dict (可选), rag\_config: dict (可选)。  
  * 响应: generated\_content: str, originality\_highlights: List\[dict\], source\_references: List\[str\]。  
* **/get\_settings (GET)** / **/update\_settings (POST)**: 管理后端配置（如默认模型、RAG参数等，如果部分配置存储在后端）。  
* **/health (GET)**: 健康检查端点，供插件检查后端服务是否运行。

### **5.2 Obsidian 插件 (JS/TS)**

#### **5.2.1 UI 组件**

* **InputView**: 实现 FR-UI-002 定义的输入界面。  
* **ResultsView**: 实现 FR-UI-004 至 FR-UI-009 定义的结果展示与编辑界面。  
* **SettingsView**: 实现 FR-UI-010 至 FR-UI-012 定义的设置面板。  
* **StatusNotifier**: 用于显示加载状态和错误提示。

#### **5.2.2 API 客户端**

* **目的**: 封装对本地 Python FastAPI 服务器的 HTTP 请求。  
* **核心逻辑**: 提供类型安全的函数来调用后端定义的各个 API 端点，处理 JSON序列化/反序列化和基本的网络错误。

#### **5.2.3 后端进程管理**

* **目的**: 简化用户启动和停止 Python 后端服务的体验。  
* **核心逻辑**: 实现 FR-MGMT-001 至 FR-MGMT-004 定义的逻辑。可能需要使用 Node.js 的 child\_process 模块来管理可执行文件。

## **6\. 数据模型 (MVP)**

### **6.1 向量存储表结构 (LanceDB)** 1

* note\_path: TEXT, PRIMARY KEY (或唯一标识符)  
* chunk\_id: TEXT (组合 note\_path 和块内序号)  
* chunk\_content: TEXT  
* chunk\_embedding: VECTOR (维度取决于嵌入模型)  
* title: TEXT (源笔记标题)  
* tags: TEXT (源笔记标签，逗号分隔)  
* last\_modified\_time: INTEGER (Unix时间戳)  
* metadata\_json: TEXT (其他自定义元数据，JSON字符串)

## **7\. 部署与安装 (MVP)** 1

* **Python AI 服务器**:

## **8\. 未来迭代路线图 (简述)** 1

* **平台支持**: 逐步增加对更多社交媒体平台的提示模板和特定适配逻辑。  
* **RAG 优化**: 引入关键词混合检索、上下文重排序、更智能的分块策略。  
* **提示工程深化**: 允许用户在UI中自定义和管理提示模板；探索元提示技术自动优化提示。  
* **原创性与质量评估**: 增强原创性检测（如与用户已发布内容比对）；引入基于LLM的自动化“平台适配度”评估模块。

* **性能优化**: 持续优化后端处理速度和资源占用，例如缓存常用嵌入。
